# Niagara scalability, deny lists, and scheduling CVars: batch H

This guide covers the 45 `fx.Niagara.*` entries left uncovered in the current community registry audit. The registry supplies the help text and types; the companion `CVarDump.txt` snapshot supplies observed values when present. The snapshot's game build and capture method are unknown, so its values are not verified defaults or recommendations. Eight string settings have no captured value in that snapshot.

The local scan targets Marvel Rivals Shipping build `1.1.4042190`. The number in the evidence column is the count of direct-memory instruction candidates targeting the registered `ref_rva`; it shows static access to the stored value, not a complete consumer path, proof the code runs in a match, or proof a startup `.ini` can change it. A count of zero is not proof the setting is unused; indirect and out-of-scope reads may not be found.

## What this establishes about changing the values

All 45 names are registered as `ref` rows in the community attachment, and the local scan contains direct value-access candidates for 44 of them. That is stronger than name or setup evidence, but it is still static analysis of one game build. `fx.Niagara.VolumeRenderer.Enabled` has no direct candidate in this scan. None of these observations proves that the mod loader accepts a particular startup `.ini` line, that the value wins over later config layers, that an affected feature is enabled in Shipping, or that changing it produces the help-described outcome in a live match. No controlled config override, live console query, or in-game comparison was performed.

For the earlier Niagara controls, see [Niagara batch E](cvar-fx-niagara-batch-e.md), [batch F](cvar-fx-niagara-batch-f.md), and [batch G](cvar-fx-niagara-batch-g.md). The [community registry guide](cvar-community-registry.md) distinguishes supplied help and snapshot values from exact-name Unreal Engine 5.9 matches. [CVar override notes](cvar-overrides.md) explain the syntax-versus-editability limits.
