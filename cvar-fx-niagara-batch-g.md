# Niagara leakage, simulation, and render-target CVars: batch G

This page covers the next 25 uncovered `fx.Niagara.*` variable entries in the community registry. Registry help and the accompanying captured values are the source for the descriptions below. The snapshot's game build and capture method are unknown, so its values are observations rather than verified defaults or recommendations.

The build scan covers Marvel Rivals Shipping build `1.1.4042190`. A direct-memory candidate means an instruction accesses the CVar value address; it is static evidence, not a full consumer trace. Address-taking references are registration/setup evidence and are not counted as value accesses.

## What this establishes about changing the values

All 25 names are registered as `ref` entries in the supplied attachment. In the scanned build, 15 have at least one direct-memory candidate at the registered value address; ten have only address-taking setup evidence or no reference match. Direct candidates show that machine instructions access storage, not that a specific branch executes during a match or that a startup `.ini` override changes the value. A `ref` label does not by itself prove the loader accepts or preserves an override.

The captured snapshot has unknown build and collection method. It conflicts with the help-stated default for `PreSkinEnableForceTick`, and the two particle-budget values happen to match; neither pattern establishes the live defaults. No controlled config override, runtime console query, render-target comparison, compilation measurement, or in-game visual/performance test was performed for this batch.

The [community CVar registry](cvar-community-registry.md) records source help and snapshot provenance; [CVar override notes](cvar-overrides.md) explain why registration and a syntactically valid `.ini` line do not prove runtime editability.
