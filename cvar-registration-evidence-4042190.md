# CVar registration evidence in build 4042190

This guide records static checks connecting community-registry address fields to CVar registration-like code in the local x64 Shipping executable. Thirty-five examples below are wired into this build's code path; this does not verify every attachment row or establish the default values shown in the snapshot.

## Inputs and method

- Local executable: `Marvel Rivals Shipping executable`, build `1.1.4042190`, SHA-256 `omitted from this documentation-only project`.
- Community inputs: [`console_vars.tsv`](https://discord.com/channels/1512820805615091712/1512825591529869383/1570970983353950322) and [`CVarDump.txt`](https://discord.com/channels/1512820805615091712/1512825591529869383/1562934699502866452). The attachment hashes and address-column cautions are in the [source notes](EVIDENCE.md#build-specific-static-analysis).
- Tool: GNU `objdump` 2.47.20260726 (Binutils for MinGW-W64 x86_64).
- PE image base: `0x140000000`.
- Disassembly uses VA addresses. For the TSV's `*_rva` fields, the examples below use `VA = ImageBase + RVA`.

The check follows each UTF-16 CVar name into `.text`, then inspects whether nearby instructions pass the corresponding `ref_rva` address and name pointer to an indirect call. It also checks the post-call stores into the `obj_rva` address range. The call target is indirect, so the snippets establish the data flow and a registration-like pattern; they do not identify the called function's source-level name.

### Bone-reduction runtime-use evidence

The client bone-reduction settings have direct reads in build 1.1.4042190, beyond their registration-like sequences in the table above. The detailed meanings and evidence limits are in the [bone-reduction guide](cvar-bone-reduction.md).

- `a.ClientReduceBoneLOD` is read at `0x143A79BF6`. Under an object-flag gate, negative values skip the special branch; nonnegative values enter its helper path only when the setting is `<=` an integer argument copied into `r13d`. This matches the community description of a minimum LOD threshold, though the argument's source-level identity is not recovered.
- A helper at `0x146844310` reads `a.ClientReduceBone.Strength` at `0x146844315` and returns a value clamped to `0..2`, consistent with its community help's three strength labels.
- `a.ClientReduceBoneLevel` is read at `0x146DCEB1F`. A value `<= 0` prevents a condition flag from being set; for positive values, the code compares an adjacent integer global with the CVar and sets the flag when the global is `<=` the CVar, subject to two other boolean checks. The community help calls this a `ViewDistanceQuality` threshold. The global's identity and the helper's full downstream effect are not independently recovered.
- `a.EnableAlwaysReduceBone` has direct runtime reads at `0x143A99428` and `0x144212266`. At the first, a nonzero value (under an object-flag gate) allows a call through virtual slot `[rax+0x688]`; at the second, a nonzero value clears bit `0x1` at object offset `0xF8B`. The object type, virtual method, and flag semantics remain unidentified, so this establishes participation in runtime logic but not a full definition.
- The full direct-reference scan found no memory-instruction candidate for `a.EnableAutoReduceBoneOnServer` matching the community `ref_rva`. This is only a scan limitation, not proof the variable is unused; indirect references or mismatched address metadata may be missed.

These static branches support the community descriptions, but do not establish visible changes, performance gains, server behavior, or safe override values. No controlled gameplay comparison was performed.

### Ragdoll distance runtime-use evidence

`a.ragdoll.LODDistance` (`ref_rva=0xF9F3134`, `float`) is loaded at `0x146DC5793` and `0x146DD6BFE`. Both paths square the setting, calculate a squared 3D distance, and compare them. The first enters additional logic only when the distance exceeds the threshold; the second enters an update path under the same condition and sets a byte flag before calling a helper. The game-specific CVar name suggests ragdoll LOD distance, but these code slices do not fully identify the object types or the downstream effect. See the [focused ragdoll note](cvar-ragdoll.md).

### Chaos scene-query BVH runtime-use evidence

The full `.text` scan found 144 direct-instruction candidates for each of `p.Chaos.SQ.UseBVH` and `p.Chaos.SQ.BVHTraversalMode`, plus 20 for `p.Chaos.SQ.SweepSingleSortInitialOverlaps`; many repeat in generated query-code copies. In one representative path, `UseBVH` is compared with zero at `0x142B4C9A8` after `edi` was cleared. A false value branches out of this path, while a nonzero value proceeds past additional object/query checks. ## Limits and next use

- These checks cover thirty-five x64 CVar examples only. They do not show that all 8,973 community `var`/`ref` names are present in build 4042190.
- The attachment does not name its source game build or dump procedure. Address matches are supporting evidence, not proof that every row's addresses align with this executable.
- Some TSV `obj_rva` values fall in a virtual-only tail rather than file-backed PE data. Some `ref_rva` values are outside the image or outside file-backed sections. Check each address before interpreting it.
- The helper call is indirect. Its argument pattern and following stores are consistent with CVar registration, but source-level registration function identity has not been recovered here.
- Repeat the same process for additional entries and retain exact instruction evidence. Do not promote a CVar's snapshot value to a default or recommendation without separate evidence.
