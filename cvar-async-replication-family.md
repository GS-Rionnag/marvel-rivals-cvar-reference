# `Net.AsyncRep.*` replication variables in build 4042190

This guide covers every `Net.AsyncRep.*` variable present in the preserved community registry (21 variables) and distinguishes those from the separate `Net.AsyncRep.RepBodyOffGT.Debug` command. It combines the attachment's descriptions with direct-reference and instruction evidence from the local x64 Shipping executable. The community attachment does not identify its capture build, so the name/address alignment is still unconfirmed.

## Main `RepBodyOffGT` path

The community help describes `Net.AsyncRep.RepBodyOffGT` as a mode: `0` is legacy; `1` moves the body of `ServerReplicateActors` work (`Gather`, `Prepare`, `Shared`, and `Copy`) onto an async task, with the game thread pumping `HandleData`.

In build 1.1.4042190, the int32 is read at `0x146C529A1`, `0x146C5D139`, `0x146C619CD`, and `0x146C619F9`. The first two inspected gates compare it with zero, so those sites distinguish disabled (`<=0`) from enabled (`>0`). At `0x146C529A1`, that check is combined with `Net.AsyncRep.RepBodyOffGT.MassPrePump > 0` and the result of the multithreading eligibility helper before a per-object flag is set. This is one setup path, not proof that MassPrePump is a global prerequisite for every RepBodyOffGT path.

The `Net.AsyncRep.Multithreading` helper at `0x1451FFE90` returns enabled only when the global bool is nonzero **and** the input object's byte at offset `0x944` is nonzero. This corroborates the community help's dependency on Multithreading while showing that the switch is also object-gated in this use.

`Net.AsyncRep.RepBodyOffGT.Pump` is checked at `0x146C5D1D3` and `0x146C5D280`. In the first site, a positive value enters a path that builds and submits a callback; zero skips it. The help says `0` leaves the replication body asynchronous but disables game-thread pumping, causing the game thread to spin at the wait. That is a community description; no timing or runtime test was performed here.

`Net.AsyncRep.RepBodyOffGT.PumpBudgetMs` is loaded at `0x1466C76C9` and passed as a float to helper `0x1466B3A80`. The community help describes it as the per-slice time cap for `HandleDataWithTime`; `<=0` means drain the queue in one slice, and an unfinished queue keeps the batch scope open for the next slice. The helper's complete timing semantics are not recovered from this instruction slice.

## Related command and limits

`Net.AsyncRep.RepBodyOffGT.Debug` is registered as a `cmd`, not a CVar. Its help says no argument or `1` enables RepBodyOffGT diagnostic logging and `0` disables it without changing replication behavior. It is listed with the [community console commands](cvar-community-commands.md), so it does not belong under the config's `[Overrides]` CVar lines.

Several help strings explicitly label zero values as legacy or diagnostic comparison modes. The docs do not establish that the new path is safe, supported by matchmaking, or beneficial for latency/performance. The capture has no pinned game version and most helper internals remain unknown; these are implementation clues, not recommended overrides. The address and attachment caveats are in the [CVar source notes](EVIDENCE.md#build-specific-static-analysis).
